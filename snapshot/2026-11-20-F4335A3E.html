What's new in PostgreSQL 19

PostgreSQL 19 is a practical release. There is no single headline feature that changes what PostgreSQL is. Instead, version 19 goes after operational problems that database teams know well: bloated tables, unstable query plans, replica lag, incomplete statistics, and maintenance work that is hard to run safely in production.

The common thread is control. PostgreSQL 19 gives you more ways to step in when the defaults are not enough, without giving up the project's bias toward reliability and predictable behavior.

The full list of changes is in the PostgreSQL 19 release notes.

REPACK

PostgreSQL uses multiversion concurrency control, so an UPDATE creates a new row version and a DELETE leaves a dead tuple behind. Routine vacuuming makes that space reusable, but it doesn't necessarily return space to the operating system or restore a useful physical row order. Over time, heavily updated tables can become bloated and poorly clustered.

The usual fixes have been VACUUM FULL, CLUSTER, or external tools such as pg_repack. The built-in commands work, but they take an ACCESS EXCLUSIVE lock for the whole operation, blocking normal access to the table.

PostgreSQL 19 adds REPACK, which reclaims space while normal reads and writes continue during most of the operation. For example, a chat application can rebuild its messages table while clustering rows by conversation and send time using an existing index:

REPACK reclaims space like VACUUM FULL; with USING INDEX, it also physically orders rows like CLUSTER. With CONCURRENTLY, PostgreSQL rebuilds the table while normal reads and writes continue, capturing ongoing changes through logical decoding. It then takes an ACCESS EXCLUSIVE lock to apply any remaining captured changes and swap the new table and index files into place. This phase is typically brief but can take longer on a busy table.

There are operational constraints. Concurrent repacking creates an additional replication slot for the duration of the operation, so it needs free capacity under max_repack_replication_slots and a table with either a non-deferrable primary key or a suitable index-based replica identity. It also needs temporary disk space for a copy of the table and all its indexes, potentially plus a sort file up to the size of the table. Tables with heavy update and delete traffic face an additional limit: the current upstream PostgreSQL 19 implementation fails if more than about 104 million tuples in the target table are updated or deleted while REPACK (CONCURRENTLY) is running. This counts changes made during the repack, not rows already in the table.

Not every relation type is eligible. Long-running transactions can delay the final lock. Concurrent repacking is also not MVCC-safe: after it commits, transactions using snapshots taken before the repack began can see the table as empty. Physical clustering also degrades as later writes arrive.

REPACK CONCURRENTLY still needs planning, but it brings into core a job that previously required more downtime or an extension.

Query plan advice

The PostgreSQL cost-based optimizer uses table statistics and cost estimates to choose an execution plan. Most of the time, that works well.

Statistics describe individual tables well, but real datasets often contain relationships that are harder to capture. Imagine that enterprise customers make up 0.1% of customers but generate 30% of orders. Per-table statistics cannot capture that cross-table correlation.

With an index on orders.customer_id, the planner may estimate that each enterprise customer has only a few orders and choose a nested loop that repeatedly probes the index. If those customers actually account for 30% of orders, each lookup returns far more rows than expected, and a hash join may be more appropriate.

PostgreSQL 19 adds pg_plan_advice and pg_stash_advice for these situations:

  • pg_plan_advice describes planner decisions as advice, applies supplied advice, and reports whether it was followed.
  • pg_stash_advice stores advice by query ID and applies it automatically when a matching query is planned

These components do not add cross-table statistics or replace the planner. Instead, they let you intervene when an inaccurate estimate produces a poor plan.

Parallel autovacuum and new statistics views

Autovacuum can now use parallel workers when vacuuming indexes, controlled by autovacuum_max_parallel_workers.  A new scoring system prioritizes eligible tables based on how urgently they need vacuuming or analysis.

New statistics views expose more of what the server is doing:

  • pg_stat_lock reports statistics by lock type.
  • pg_stat_recovery shows recovery status.
  • pg_stat_autovacuum_scores shows how autovacuum prioritizes tables.

Query-level diagnostics improve as well. EXPLAIN (ANALYZE, IO) reports asynchronous I/O activity, and auto_explain.log_io can include the same information in logged plans.

PostgreSQL 19 also reports bytes written for full-page images in pg_stat_wal, EXPLAIN (ANALYZE, WAL), and vacuum and analyze logs.

Together, these make performance investigations less dependent on inference. You can see why maintenance work was prioritized, where asynchronous I/O happened, and how many WAL bytes came from full-page images.

Logical replication

Logical replication has become core infrastructure for change data capture, migrations, real-time serving, and ETL pipelines. PostgreSQL 19 closes several long-standing gaps:

  • Logical decoding can be activated without a restart when wal_level is replica. Creating the first valid logical replication slot raises effective_wal_level to logical, showing the WAL level currently in effect.
  • Sequence values can be synchronized from publishers to subscribers.
  • Publications can include all sequences with FOR ALL SEQUENCES.
  • CREATE PUBLICATION ... FOR ALL TABLES EXCEPT (...) publishes all tables except a named set.
  • Subscriptions can reuse connection details from a postgres_fdw server with CREATE SUBSCRIPTION ... SERVER.
  • The retain_dead_tuples subscription option preserves enough information to detect update_deleted conflicts, where a replicated update targets a row deleted by another origin. Detection also requires track_commit_timestamp on the subscriber, and pg_stat_subscription_stats counts these conflicts.

Sequence synchronization removes an awkward migration edge case, especially during major-version upgrades that use logical replication. Copying table rows without advancing their sequences can leave a promoted subscriber generating values that already exist, causing duplicate-key errors.

WAIT FOR LSN

Asynchronous read replicas add read capacity without making primary commits wait for them. The tradeoff is replication lag. An application can commit a write on the primary, immediately read from a replica, and not find the row because the replica has not replayed the relevant WAL yet. 

PostgreSQL 19 adds a direct way to coordinate that handoff. An LSN identifies a position in the PostgreSQL WAL, and WAIT FOR LSN blocks the standby until replay reaches at least the requested position:

By default, WAIT FOR LSN waits indefinitely for the standby to replay the requested LSN. Other modes can wait for WAL to be written or flushed, and you can set a timeout.

The client or connection pooler still has to carry the LSN from the primary to the replica. The database now provides the missing synchronization step, so read-your-writes behavior no longer needs polling or arbitrary sleeps.

Statistics import for postgres_fdw

Foreign data wrappers let PostgreSQL query remote systems as if their data were local. Planning those queries has always been hard when the local optimizer does not know the remote table’s size or data distribution.

PostgreSQL 19 lets postgres_fdw import statistics from the remote server:

ANALYZE imports the existing remote statistics into the local server. If the import fails, postgres_fdw falls back to row sampling. The remote statistics therefore need to be current.

Without remote statistics, PostgreSQL may rely on fallback size estimates and choose a nested loop. After importing them, the planner can estimate row counts more accurately and may choose a hash join instead.

Federated queries still pay network and remote-system costs, but accurate row estimates remove a major source of avoidable bad plans.

Smaller SQL and performance changes

Lastly, a few compact changes with a quality-of-life payoff:

  • JSON path expressions gain familiar string methods such as btrim(), lower(), replace(), and split_part().
  • The random(min, max) family now supports date, timestamp, and timestamptz, which helps with tests and synthetic datasets.
  • Five window functions accept IGNORE NULLS and RESPECT NULLS.
  • When io_method = worker, I/O workers scale automatically between io_min_workers and io_max_workers. Foreign-key checks are faster, and the planner and executor get another round of targeted optimizations.

We also lost a few features

Several major features landed during PostgreSQL 19 development but were removed before release. Reviewers found correctness or design problems that were too risky to resolve late in the cycle, so the community held the features for a later release.

Some of the features that finally won't ship in 19:

  • SQL/PGQ property graph queries. CREATE PROPERTY GRAPH and GRAPH_TABLE brought graph pattern matching over regular tables into SQL. Reverted on September 7, 2026.
  • UPDATE and DELETE ... FOR PORTION OF. Temporal updates and deletes that split rows to preserve history outside the targeted time range.  Reverted on September 15, 2026.
  • ALTER TABLE ... MERGE PARTITIONS and SPLIT PARTITION. Built-in commands for combining or dividing partitions. Reverted on August 27, 2026.
  • GROUP BY ALL. Shorthand for grouping by every non-aggregate expression in the select list.. Reverted on July 17, 2026.
  • Non-text output formats for pg_dumpall.  Reverted on June 18, 2026.
  • DDL extraction functions. pg_get_role_ddl(), pg_get_tablespace_ddl(), and pg_get_database_ddl() were Reverted on September 13, 2026.

Upgrading to PostgreSQL 19

As with any new major version of PostgreSQL, we recommend a measured approach to adopting it. Before moving production workloads to 19.0, we suggest you:

  • Test your own workloads, queries, and extensions on PostgreSQL 19 in a development or staging environment first
  • Compare performance and behavior against your current version, since major releases can change query plans and defaults
  • Check that the extensions you rely on are available on PostgreSQL 19 (see below).
  • Keep production on your current version until you're comfortable with the results

PostgreSQL19 also changes several defaults and compatibility behaviors. Check these before you upgrade:

  • JIT compilation is off by default
  • TOAST compression defaults to LZ4 instead of pglz
  • MD5 password authentication emits stronger deprecation warnings
  • RADIUS authentication support is removed
  • standard_conforming_strings is always on
  • pg_upgrade rejects clusters with affected btree_gist indexes on inet or cidr
  • Database, role, and tablespace names can no longer contain carriage returns or line feeds

A note on extensions

We've covered most of the extensions supported in our PostgreSQL 18 release, but not all of them are available on PostgreSQL 19 yet. We're adding more as they become available from the extension providers. If your workload depends on a specific extension, confirm it's available on PostgreSQL 19 before you plan a migration.
